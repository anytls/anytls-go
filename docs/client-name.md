# 关于 AnyTLS `client` 字段争议的说明

近期，部分社区围绕 AnyTLS `cmdSettings` 中的 `client` 字段出现了一些争议。我们希望说明这一字段的设计考虑，并回应客户端、服务端运营者和用户各自关心的问题。

本文发布于 2026-08-03，仅代表写作当时的情况。

## 字段定位

`client` 用于声明客户端软件名称及版本，例如 `anytls-go/0.0.1`。

从用途上看，它接近 HTTP 中的 User-Agent：客户端默认告知服务端自己使用的实现和版本，服务端可据此排查故障、统计实现分布、分析兼容性问题，也可以在处理异常连接时将其作为辅助参考。

和 User-Agent 一样，这类信息由客户端自行声明，用户可以修改，服务端不能据此可靠确认客户端实际使用的实现。

`client` 位于加密连接内部，普通的被动网络观察者无法直接读取。其内容通常只包括软件名称和版本，不含用户身份、设备标识等个人信息。

## 客户端默认行为

我们仍建议第三方实现默认上报真实的软件名称和版本。用户若有特殊需求，可以自行关闭或修改该字段。

默认如实发送有利于故障定位和生态协作。若所有实现都默认留空，服务端只能看到缺乏来源说明的连接，出现问题时也更难判断影响范围。

此前协议文档中“伪装没有任何意义”的说法过于绝对，应当修正。

## 关于服务端限制

服务端运营者有权根据滥用、凭据泄露和主动探测等风险制定连接策略，但限制手段的有效性和合理性仍需分别评估。

目前已知有 **部分特定服务商** 针对 `client` 字段采取了直接限制的措施。由于公开信息有限，我们无法还原各方内部决策过程，也不对具体限制原因或动机作进一步判断。

`client` 可以参与异常连接分析，但单独依靠它长期封禁某类客户端，效果有限，也容易误伤正常用户。

## 关于第三方实现

第三方项目可以根据自身定位提供隐私选项，也可以允许用户自定义元数据。

我们理解部分客户端希望减少默认上报信息，也尊重项目维护者作出自己的产品选择。但将字段默认置空，会偏离现有协议文档的推荐行为，并减少服务端可获得的诊断信息。此类修改更适合先在协议仓库公开讨论，说明实际风险、兼容影响和替代方案。

**仅凭个别服务商的处理方式，将整个字段概括为设计缺陷或认为其毫无合理用途，属于扩大指控，没有充分依据。**

## 后续方向

反审查协议面对的挑战不仅有被动特征审查，还有主动探测、凭据滥用以及不同实现之间的兼容问题。客户端开发者、用户和服务端运营者承担的风险不同，但都依赖协议生态持续可用。

我们将保留 `client` 字段，并继续建议客户端默认上报真实的软件名称和版本。

关于该字段的后续使用，我们建议遵循以下原则：

* 将 `client` 定义为类似 User-Agent 的，区分不同实现的元数据；
* 客户端默认上报真实的软件名称和版本，同时可以提供合理的修改或关闭方式；
* 服务端只将其用于诊断、统计或辅助风控，不要直接将其作为封禁依据；
* 部分服务商依据该字段采取限制措施时，应考虑误伤风险，并尊重用户对规则和决策过程的知情权。

我们欢迎客户端开发者、服务端实现者、运营者和用户基于具体事实参与讨论。客户端有保护用户选择、提供隐私控制的责任；服务端也有维护服务稳定、防范滥用和处理异常流量的现实需求。**双方诉求并非完全对立，不应将一个具体的协议设计分歧扩大化指控，也应避免在缺乏充分协调的情况下单方面改变默认行为，使用户被动承担服务端策略或客户端行为变化带来的影响。**

最终目标应当是让用户获得稳定、可选择的服务，让客户端实现保持开放发展，也让服务端运营者具备合理的管理能力。通过沟通解决分歧，比通过对抗制造新的兼容性分歧，更符合 AnyTLS 生态的长期利益。

## 总结

上述争议主要发生在用户使用第三方代理服务时。

部分机场仅凭可伪造的 `client` 字段限制特定客户端，识别效果有限，也容易误伤正常用户；相关规则、原因和申诉方式应当尽量公开。

另一方面，sing-box 在缺乏充分协议讨论和兼容性评估的情况下直接将字段默认禁用，并将该字段概括为隐私缺陷，也会放大争议。客户端可以提供关闭或修改选项，但不应单方面重新定义协议边界。

希望双方在现有立场上作出适当调整：相关服务商不再仅依据可由客户端自行声明的 `client` 字段实施硬性限制，而是采用结合多种信号、能够降低误伤风险的反滥用策略；sing-box 也应避免将该字段笼统定性为隐私缺陷，重新评估默认禁用的做法，并在保留用户修改或关闭选项的同时，恢复默认上报真实客户端名称和版本。
